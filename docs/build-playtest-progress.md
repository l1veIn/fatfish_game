## 当前判断

| 方向 | 当前可执行的操作 | 现在最需要验证 |
|---|---|---|
| 顿悟青菜 | 一级炒菜、禁番茄炒蛋；训练→回甘→连续单品。关闭融合/Temperature 做对照，助手补主食 | 启动时间、付费口数与融合换密度的实际取舍；保留用户已验证的爽感 |
| 单品轮换 | 包子/鸡腿分盒轮换；把点心与油炸放在相邻档位；可插入一次小套餐充缓存 | 新手能否稳定轮换、断线后几盒恢复；不要把理论满连击当常驻 |
| 保温收尾 | 关闭满盒回收，按需暂停 Best-of-N；普通餐维持吞吐，手动留高品质高单口盒给 Final/EOS | 留盒/等料损失、最好一口是否真正兑现；总盒价与最好一口不是同一个目标 |
| 均衡评鉴 | 给助手指定不同简单套餐；玩家补新种与营养；看评鉴已吃种类 | 一局第五种/第九种何时真正吃掉；做出或发现不等于吃掉 |
| 助手分工 | 补漏、指定配餐、补营养分别工作；玩家消费接力 | 配方等待、重复订单争料、异步优先级与实际省操作量 |
| 高温随机 | 低级供给经 Temperature 越级/升品质；杂菜临场合成；按需开重新生成 | 容量已作整局检查；还须判断随机收益、装盒可理解性和真人临场选择 |

缓存作为轮换/套餐的配套节奏，不单独算第七条。六条可以混搭，记录中不按分数自动贴流派标签。助手有效订单、接力以及随机容量的自动回归，只证明机制能运行，不证明六种成熟或平衡。

## 本轮修复与记录

接菜 Temperature 原来已有最终容量检查；本轮查到送达后的重新生成仍会扩大菜的占格，现逐份按真实两行装盒检查。放不下时原菜升品质并加热，保留原有先冻结送餐奖励、再重抽、不额外合成的顺序。规则夹具覆盖四格满盒、留空成功升级、六格行碎片、鬼菜与套餐免重抽。

**保温流控制补充**：助手分工→自动操作新增 Best-of-N 开关，已购技能默认仍开启；暂停后保温箱继续可用，玩家手动留盒，不必退款。旧存档不受影响，配置下顿生效。自动选择仍按整盒裸价值，不暗改为 EOS 算法；技能文案明确这项取舍。原来的六张开关卡不移动，在页底补一条保温选盒开关。

新局结束后将最近 30 局存于 `%APPDATA%/FatFishFreeLunch/save_meals/`，每局独立 JSON。游戏存档仍是原来的 `save.json`，记录失败不阻止结算；本机记录，不上传。QA 使用各自 `qa_<profile>_meals/`；自动测试、调试、普通手动操作明确标记。历史最高分无法补录归因。

每份记录包括：

- 开局版本阶段、技能等级及累计购点花费（不含版本门票/评测费）、有效禁菜/招牌、助手职责、有效自动行为状态、档口顺序和规则文件哈希。
- 每种菜从档口成功抛出的数量、进入各自饭盒的接触次数、顿悟训练/拒吃/正常吃掉数量；鬼菜单列。**接触次数不是唯一食材数**：打翻后重新接住会再次计数。自动合成会消耗多个原料形成一口，不能用成品口数减原料数来算漏接。
- 每盒玩家提交、送达、开吃、进入/离开保温的时间与菜品；实际冻结的连击、缓存/轮换、助手接力。每局最多 2048 个盒事件，若截断有显式计数。
- 每 5 秒营养轨迹、首顿悟世界时间、正常/保温/剩菜付费口数、真正吃掉的套餐 ID、主动游戏时长（不含暂停/开场教学）。
- 局中收入、保温、EOS、剩菜、裁剪与整顿倍率。保温和 EOS 占比以整顿乘法前的小计为分母，两者互不重叠；EOS 是重复计钱，不增加吃掉的口数。

## 怎么做同预算真人比较

先固定一个共同预算上限与阶段；不同路线不一定恰好花光，工具同时显示实际投入范围。四条主路线各三局，再补助手/随机。换顺序避免把熟练度增长误当构筑增长。旧文的五套示例成本不同，不能直接拿来做强弱排名。

```powershell
python pipeline/compare_meals.py "$env:APPDATA/FatFishFreeLunch/save_meals" --csv build/meals.csv
```

第一步只汇总，不猜流派。真人测试后用自己的文件名填写 JSON 标注，例如 `build/playtest-labels.json`：

```json
{
  "meal_实际文件名.json": {
    "route": "greens",
    "budget_cap": 4000000,
    "player": "tester-a",
    "device": "mouse-keyboard",
    "pressure": 2,
    "recovery": "断了一盒，下一盒重新开始",
    "notes": "实际感受；是否混搭保温/助手"
  }
}
```

`route` 可填 `greens`、`rotation`、`warm`、`review`、`helpers`、`random`。上面的 400 万只是格式示例，不代表已完成共同预算方案。`pressure` 是真人操作压力 1–5；`recovery` 没有遇到中断就如实写没有。

```powershell
python pipeline/compare_meals.py "$env:APPDATA/FatFishFreeLunch/save_meals" --manifest build/playtest-labels.json --csv build/meals.csv
```

只有相同规则哈希、游戏版本、阶段、局长、预算上限、操作者与设备的完整普通手动局进入同组；自动测试、评测局、提前退出、超预算和截断记录只列明细。输出中位数、范围、实际花费和压力，不根据最高分宣布路线优胜。每盒事件仍需结合真人备注解释失败恢复。

导出包会把 GDScript 编译为字节码，记录会跟随 `.remap` 计算实际文件哈希并记录路径，不把源码哈希冒充字节码哈希；编辑器与导出包因此分组比较。缺少任何规则哈希的局也不能进入正式比较。

## 验收命令

```powershell
python pipeline/validate_release.py --visual --uncapped-ui --only random-shift --only random-shift-visual --only helper-strategy --only mechanics --only controls
```

随机整局用合法等级、正常出勺、下落、实际接触和结算；机器人接菜，固定小步长，概率不强制。四/六/八格各一整顿，逐步检查手持、助手、配送、队列、保温和进食中的盒子；GPU 截图另行检查。不是同预算比赛、真人手感或设备性能测试。详细报告和源码/真实存档哈希由验收脚本保存。
